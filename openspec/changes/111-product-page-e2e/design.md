## Context

Change 82 gave `tests/e2e/fixtures/test.ts` (a `test.extend` with an automatic `dummyJson` fixture: `requests`, `violations`, `hold(match) → { arrived, release, outcome }`, an origin guard) and `mockDummyJson(page, overrides?)` with `overrides.product` (the stub answers `/products/<id>` only for the id of `fixtures.product`). The product page: route `/products/:id` with `HydrateFallback: ContainerLoader` (`src/app/router/router.tsx:31`) and a loader (`:32-44`) that calls `resolveProductDetails` and throws a `404` response for not-found; the page (`src/pages/product-details/product-details-page.tsx`) shows `ContainerLoader` while the revalidator loads, the `Back to products` link from `location.state.from`, the `ErrorAlert` with `Try again` → `revalidator.revalidate()`, and the content. The layout shows a loader while a navigation loads (`src/app/layouts/main-layout/main-layout.tsx:19`).

## Goals / Non-Goals

Goals: browser proof of the `product-details` wiring; a stub that can fail a request in each way the spec names.

Non-goals: product behaviour; product content and data cases as separate e2e tests (see below); the helpers already proven by units (`product-back-link.test.ts`, `product-view.test.ts`, `resolve-product-details.test.ts`); the not-found page's own content (spec `not-found-page`); other browsers.

## Decisions

- **Failing a request in the stub.** `handle.fail(match, failure)` — `match` as in `hold` (a `path + search` string or a predicate); `failure` is `{ status: number }` (answered with that status, an empty JSON body and the stub's `CORS_HEADERS` — without them `fetch` rejects and the app shows "No connection") or `"network"` (`route.abort("internetdisconnected")`). A failure is checked before the stub's routing (any DummyJSON path can fail, with or without a fixture). Only the **first** matching request fails; later ones get the normal answer (so a retry can succeed). Failed requests are logged in `requests` and are not violations. `fail` and `hold` may target the same path: `fail` applies to the first match, `hold` to the first match not taken by `fail` — the retry test fails the first request and holds the second.
- **What stays below e2e (spec/05, lowest layer).** The project has no component-test layer (no testing library), so the lowest layer that sees the page's markup is e2e — but the data cases stay unit-level: the photo fallback for a product without images (`getProductPhoto`, `product-view.test.ts`), the price format (`formatUsdPrice`), a response of the wrong shape (`get-product-by-id.test.ts`: "throws RequestError for a wrong shape"; the error path itself is proven in e2e by the 500 test). e2e only proves the wiring: the direct-open test checks as steps that the page shows the product (alt, heading, price, description) with the stubbed product, no separate content test.
- **Back to a filtered catalog is not repeated.** `catalog.spec.ts` "leaving the catalog and coming back" already opens a product from a filtered catalog and returns with `Back to products` to `/product?q=phone`; dropping the link state turns it red. Search and category share the same `location.search`, so a category variant would be a duplicate (spec/05 §9). This change keeps only Back after a direct open.
- **The held-without-fixture gap (verify 82, W1).** A held request with no fixture is fulfilled with an empty list today (`mock-dummy-json.ts:261-266`), unlike the unheld path, which records it as a violation (`:162-166`) — against change 82 `design.md`. Task 1.1 aligns the held path, since this change adds holds.
- **One spec file, scenario per test.** `tests/e2e/product-details.spec.ts`, each test with its own `page.goto`, steps by `test.step`, role/label locators (`getByRole("heading", { level: 1 })`, `getByRole("img", { name })`, `getByRole("link", { name: "Back to products" })`, `getByRole("alert")`, `getByRole("button", { name: "Try again" })`, `getByRole("progressbar")`), no `waitForTimeout`; loading is proven with `hold` (the indicator is asserted while the response is parked, then `release()`).
- **No reload on retry.** Before `Try again` the test sets a marker on `window`; after the content appears the marker is still there.
- **Not-found without a request.** For `/products/abc` the test asserts that `requests` has no `/products/abc` (and no `/products/` product request at all).
- **Why e2e and not lower.** The helpers are unit-tested; what breaks unnoticed is the wiring between router, loader, link state, revalidator and layout. Each test names its mutation in `tasks.md` that must turn it red.
- **e2e-map (team rules).** After the tests are on main: `src/pages/product-details/**`, `src/app/router/**`, `src/app/layouts/main-layout/**`, `src/shared/ui/error-alert/**`, `src/shared/ui/container-loader/**` → `tests/e2e/product-details.spec.ts`; `src/features/products/**` also includes it (`tests/e2e/fixtures/**` already maps to every spec) (in the format the overlay supports — checked with `ai-team gate --plan`).

## Risks / Trade-offs

- [Abort reason] `route.abort("internetdisconnected")` makes `fetch` reject; the app marks it a network error (`request.ts:106-109`) and shows the `No connection …` text (checked in review #114).
- [Loader timing] The direct-open indicator is the `HydrateFallback`; the in-app one is the layout's navigation loader; with a parked response both are stable, no timing involved.
